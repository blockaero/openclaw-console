# ARM CI write-traps: certification ladder before the guard may call a tool

Status: plan and spec only. This file does not add a test, a workflow, or application code. It does not call ARM, MCP, Neon, or a model provider. It does not mint a key. It does not merge to `main` or to any pull request. The parent plan is [PR #1](https://github.com/blockaero/openclaw-console/pull/1), file `docs/plans/openclaw-arm-readonly-smoke.md`. This spec is the thread that file's section 15 names for CI write-traps, and it follows that file's section 13 allow-list phases and decision 5.

**Verified in this repo.** `blockaero/openclaw-console` does not contain ARM source. The only application text on the parent branch is the smoke plan and `README.md`. Nothing in this checkout can run an ARM handler, open `app/principal_envelope.py`, or execute `SET TRANSACTION READ ONLY` against ARM's database. The tests described below are not implemented here. They would live in ARM CI.

## 1. What has to be true before a call

Two stacks, both required. Section 13 of the smoke plan already says they stack. This file does not replace either one with the other.

1. The certification ladder C0 through C4, then C5 when the run is unattended.
2. The fail-closed `tools/list` subset check. One extra name halts. The guard does not skip the bad tool and continue.

The mint gate stays in front of both. Write-traps do not replace it, and passing a trap does not authorize a key.

### Mint gate (unchanged)

No key is minted until ARM has a real read-only level. That level is not an alias of L0. Ledger tools stay closed to bots. An unknown level is still L0. The level has no briefing writes, no runtime-usage writes, and a no-processing mode: a read does not start Claude, OCR, classification, extraction, or an enqueue, and a missing artifact comes back as stored text or a gap. `initialize` for that level follows decision 5. This document does not build that level. A session for that server spec already exists; this file does not open a second one.

C2 and C3 are how that level, once it exists in the ARM repo, is held in CI. They are not a substitute for shipping the level, and they are not a reason to mint against today's envelope.

### Decision 5 is decided

**Decided 2026-10-05 by Todd. Not open.** The `initialize` write-trap must allow exactly one server-generated last-seen timestamp, and must fail on `last_briefing_*` content, counters, runtime usage, status, or any processing. Decision 2 is not rewritten. Later `tools/call` rows still follow decision 2: `principals.last_seen_at`, `principal_credentials.last_used_at`, and a `chat_run_leases` presence heartbeat for that principal. The handshake allow-list is narrower than decision 2. An initialize that also moves the credential `last_used_at` or inserts a lease fails the initialize trap. That does not remove those columns from later calls.

"Allow exactly one" is the allow-list, not a demand that the timestamp always change. Zero writes on `initialize` passes. One server-generated last-seen timestamp passes. A second write fails. A client-supplied timestamp, briefing body, counter, or status fails, because the allowed value is generated by the server.

The column the smoke plan's schema read named for that timestamp is `principals.last_seen_at`. This document did not re-read Neon. If ARM CI finds a different single timestamp column, the trap still allows only one server-generated last-seen timestamp and still fails the banned classes. It does not grow into decision 2.

### Decision 2 is not rewritten

This spec does not suppress `principals.last_seen_at`, `principal_credentials.last_used_at`, or the presence lease, and it does not add columns to that list. Section 14 of the smoke plan still owns the question of whether a later standing reader must suppress them. Until that question is answered there, C3 allows those columns on later calls and nowhere else.

## 3. Ladder order

A tool name is eligible for the standing guard only after the rows above it in this table have passed. The smoke key is not waiting on C5. Unattended runs are.

| Step | Who runs it | Guards which call | Blocks the smoke key? |
|---|---|---|---|
| Mint gate | ARM server change, then an admin mints | Any use of a new key | Yes. The key does not exist until the real read-only level exists. |
| C0 declare | Author, in the ARM repo | That tool | No |
| C1 review | A human reviewer in the ARM repo | That tool | No |
| C2 CI write-trap | ARM CI, not production | That tool's handler, including `initialize` | No. The trap does not mint, and minting does not skip the trap. |
| C3 Neon-branch diff | ARM CI, disposable branch | The same handler | No |
| C4 attended canary | Option B in [PR #1](https://github.com/blockaero/openclaw-console/pull/1) | That tool, attended, quiet window | No. C4 is the smoke. It uses the key after the mint gate. |
| Subset check | Guard precheck, every run | The whole `tools/list` | No |
| C5 receipt and audit | Every later run | Unattended runs of that tool | No. C5 is before unattended runs, not before the smoke key. |

Phase 2 of the standing reader is attended and template-only, in a quiet window, after C4. Unattended runs wait on C5 and on the other gates the smoke plan already lists and this file does not move: log rows attributable to a principal, a per-release manifest, and a server kill flag.

The doc-derived names that would have to climb this ladder before the guard calls them are the phase-2 status tools already listed in the smoke plan: `get_pulse_head`, `get_account_pulse`, `get_standing_playbook`, `get_deliverable_rollup`, `list_work_items`, `list_priority_part_lists`, `get_project_status`, and `registry_insights` only when that exact name is advertised. `get_briefing` stays off. This document does not certify any of those names. Passing the ladder is a later ARM CI result, not a claim in this pull request.

## 4. C0 — declare the side-effect class

Before review, the tool author records a declaration in the ARM repository. The declaration is data a reviewer and CI can read. A prompt is not a declaration.

Required fields:

- Exact tool name, the string `tools/list` would advertise. No prefix invented here (`arm__` stays unverified, smoke plan section 14).
- Side-effect class, one of the four below.
- Columns the handler may change. Empty for pure-read. For `initialize`, the single last-seen timestamp and nothing else.
- Provider and queue calls. For any class the guard may eventually call, this list is empty: no Claude, no OCR, no classify, no extract, no enqueue.
- A statement that a missing artifact is returned as stored text or a gap.

| Class | What it declares | Eligible for the guard? |
|---|---|---|
| `pure-read` | No business write. No provider call. No enqueue. Decision 2 residue, if the server still performs it, is not a license to write anything else. | Only after C1–C4, and C5 before unattended use. |
| `handshake` | `initialize` only. Decision 5: at most one server-generated last-seen timestamp. | The guard may send `initialize` as session start after the same traps. It is not a read tool the guard forwards to a job. |
| `decision-2-residue` | Not a tool. The tolerated columns on a later `tools/call`, as decision 2 already states. | Cannot be declared as a new callable. |
| `mutator` | Claim, complete, post message, put pulse head, briefing write, runtime-usage report, ledger, form, offer, or any processing. | Never. C0 of this class ends the ladder for the guard. |

A declaration that lists `last_briefing_*`, a counter, runtime usage, or a status column as allowed on `initialize` is a failed C0. It is not sent to review as a read-only candidate. Decision 5 is not a field the author can reopen.

## 5. C1 — review

A human reviewer other than the author accepts or rejects the declaration against the handler in `github.com/Block-Aero/block-aero-ai-records-manager`. <!-- pragma: allowlist secret -->

The reviewer checks:

- The class matches the handler. A read that calls Claude, OCR, classify, extract, or enqueue is `mutator` for this ladder, even if the SQL statement is a `SELECT`.
- `initialize` matches decision 5 and does not rewrite decision 2.
- Ledger tools stay closed. The declaration does not smuggle one in as a read.
- The name is not `get_briefing`.

Review is recorded in that repository's review trail. This pull request is not that review. An unreviewed declaration has not passed C1, and the guard treats the tool as uncertified.

## 6. C2 — CI write-trap

ARM CI runs this against the handler in the ARM repository. It does not call production MCP. It does not use a live pin.

### `SET TRANSACTION READ ONLY`

For a handler declared `pure-read`, the test opens the transaction that reads business data and sets it read only (`SET TRANSACTION READ ONLY`) before the handler runs. Any `INSERT`, `UPDATE`, or `DELETE` in that transaction is a failed test. Postgres rejecting the write is the trap, not a warning the test swallows.

That read-only transaction is the business read. It is not a repeal of decision 2. Decision 2's accepted residue, if the server still performs it on a later call, is judged by the column diff in C3. It is not judged by turning the read-only trap off on the business tables. If today's code writes the residue inside the same transaction as the business read, splitting or narrowing that write is ARM work in the ARM repo, required before C2 can pass. This document does not make that split. It also does not forbid the decision 2 columns on later calls.

`initialize` is not wrapped in a blanket read-only transaction. Decision 5 allows one server-generated last-seen timestamp, and a blanket `SET TRANSACTION READ ONLY` would reject that allowed write. The initialize trap is the column and provider assertions below. Using the read-only transaction as the only initialize check would contradict decision 5. Do not "simplify" the handshake into that form.

### Initialize assertions (decision 5)

On `initialize` for the read-only level, the test fails if any of these are true:

- More than one cell changed.
- The changed cell is not one server-generated last-seen timestamp. A timestamp taken from the JSON-RPC params fails. A briefing body fails.
- Any `principals.last_briefing_*` value changed, including `last_briefing_version`, `last_briefing_at`, and `last_briefing_via`. Content and the columns that hold it both fail.
- A counter changed.
- Runtime usage changed: a new or updated `arm_agent_runtime_usage` row, or a call path that is `report_runtime_usage`.
- A status changed: principal status, lease status, work-item status, `account_runtime_status`, or any other status column.
- The handler started processing.

Zero changed cells passes this trap.

### Provider and queue traps

Independent of the SQL transaction, the test installs a trap on each of these entry points. Invoking any one of them fails the test:

- Claude (the production health surface reports `vision_provider=claude`; the trap fails a handler that calls that provider).
- OCR.
- classify.
- extract.
- enqueue.

The trap is an in-process spy or stub in ARM CI. It must fail when the handler calls the function. A comment in the handler is not the trap. A missing artifact must come back as stored text or a gap. The test includes that case: no stored text, no bytes fetched from object storage, and the spy count stays zero.

These traps cover `initialize` and every `pure-read` handler submitted to the ladder. A handler that "only sometimes" calls Claude fails.

### What C2 does not do

- It does not mint a key and does not call `tools/list` on production.
- It does not replace the mint gate. A green trap on a branch build is not the read-only level in production, and it is not an alias that makes unknown levels read-only.
- It does not rewrite decision 2 into a zero-write rule or into a wider allow-list.
- It does not live in this repository, and this repository must not gain a workflow that runs it against production ARM.

## 7. C3 — Neon-branch diff

After C2's in-process traps, ARM CI runs the same handler once against a Neon branch created for that job. The branch is not the production branch. The job drops it when the diff is recorded. This document does not create a branch and did not query Neon while it was written.

The diff is against the parent of that disposable branch, or against a before-image taken on it at the start of the test. The allowed delta:

| Call | May change | Fails the diff |
|---|---|---|
| `initialize` | Nothing, or exactly one server-generated last-seen timestamp (decision 5). | `last_briefing_*`, counters, runtime usage, status, processing, any second column, decision 2's other columns (credential last-used, presence lease). |
| Later `tools/call` for a `pure-read` tool | Decision 2 only, and only for the principal under test: `principals.last_seen_at`, `principal_credentials.last_used_at`, and a `chat_run_leases` heartbeat for that `principal_id`. | Every other write. `part_identities.last_seen_at`, `account_users.last_seen_at`, and business `updated_at` fail. |

The log tables the smoke plan already fails on a new row also fail C3: `pipeline_log`, `chain_operations`, `asset_write_ledger`, `email_log`, `arm_agent_runtime_usage`, and `agent_work_items` changes to `claimed_at`, `claimed_by`, `status`, `finished_at`, or `result`. There is no table named `audit`. `login_events` stays the open item in section 14 of the smoke plan. This spec does not allow a new `login_events` row and does not close that question.

A diff the job cannot compute is a failure. It is not an empty diff.

## 8. C4 — attended canary

C4 is option B in the smoke plan, [PR #1](https://github.com/blockaero/openclaw-console/pull/1). It is not a second canary design and not an unattended job.

Attended means a person is present for the window. The live worker is quiesced so it cannot claim or complete. The harness is the option B client: dedicated read-only key, client allow-list in code, model step outside OpenClaw with tools omitted, through the MSI Ops console capture path. `openclaw_mcp_exercised` stays false. The live agent `baseUrl` stays `http://127.0.0.1:11434`. Nothing in C4 starts a gateway on port 8788.

A tool the guard will later call must have been in a passing option B run. The mid-image and after-image in that run are the canary: the handshake delta is decision 5 only, and later deltas are decision 2 only. A `last_briefing_*` change fails that account. A tool that was not in the passing run is not certified, even if C0–C3 are green.

Passing C4 does not grant the live agent write tools, and it does not start unattended runs. The smoke key used for C4 exists only because the mint gate already passed. C5 is not a prerequisite for that key.

## 9. C5 — receipt and audit on every later run

C5 is the gate before unattended runs. It is not a gate before the smoke key, and it is not a gate before the attended option B canary.

Once a tool is used on an unattended run, every later run of that tool carries both:

- A receipt for the call, sufficient to show that this call did not enqueue processing and did not invoke a server-side model (Claude or otherwise).
- An audit diff for the window, with the same allow-list as C3: decision 5 on `initialize`, decision 2 on later calls, and a failure on `last_briefing_*`, counters, runtime usage, status, or processing.

A missing receipt, a receipt that shows processing or a model call, or an audit that cannot be finished fails the run. An unfinished audit quarantines the output. It is not treated as clean. A late processing row retracts the output and halts, matching the smoke plan's `LATE_AUDIT` state. Replay of a sealed snapshot does not call ARM and does not mint a fresh receipt by calling production.

The on-wire shape of the receipt is still open. Smoke plan section 14 item 5 records the unset choice between a result field such as `processing_enqueued` / `models_invoked` and a per-call receipt in `result._meta`. This spec requires that some receipt and some audit exist and are checked. It does not pick the shape, and it does not reopen decision 5 in order to pick it.

## 10. Fail-closed `tools/list` subset check

This check is Grok's rule from section 13, stacked on the ladder. It runs in the guard's precheck on every run, including the attended phase-2 window. This document specifies it. It does not execute `tools/list`.

Rules:

- The static allow-list is code in the guard. A prompt is not the list. Membership on that list still requires C0–C4 for an attended guard call, and C5 as well before an unattended call.
- `tools/list` on the read-only key must be a subset of that static list.
- One extra name halts the run. The count of one is enough. The guard does not skip the bad tool, drop it from the working set, and continue with the other names.
- The guard does not call the extra name.
- The raw advertised list and the extra name are part of the halt record.
- A name on the static list that the server does not advertise is not called. That absence does not by itself halt, because the rule is subset, not equality. `registry_insights` remains the existing example: call it only when the exact name is advertised.
- `initialize` that advertises `sampling/createMessage` or `roots/list` is an error, then a halt, as section 13 already says. `notifications/tools/list_changed` drops permission and rechecks the catalog. A recheck that finds one extra name halts. It does not proceed with the previous catalog.

The subset check is not a certification. A name can be advertised and still be uncertified. The guard calls the intersection of the static list, the advertised list, and the names that have passed the ladder. An extra advertised name never reaches that intersection, because the run has already halted.

## 11. Assertion summary for ARM CI

The tests live in ARM CI in `github.com/Block-Aero/block-aero-ai-records-manager`. <!-- pragma: allowlist secret --> This table is what those tests assert. It is not a workflow, and it is not a test module in this repository.

| Assertion | Pass | Fail |
|---|---|---|
| Pure-read business transaction | `SET TRANSACTION READ ONLY`, and the handler returns. | Any write statement in that transaction. |
| `initialize` write | No write, or exactly one server-generated last-seen timestamp. | `last_briefing_*` content, a counter, runtime usage, status, any processing, or any other column. |
| Provider trap | Spy count stays zero for Claude, OCR, classify, extract, and enqueue, including the missing-artifact case. | Any one of those calls. |
| Neon-branch diff | Decision 5 on `initialize`. Decision 2 on later calls. | Any other delta, or a diff that cannot be computed. |
| Production | The job never connects to production ARM or the production database. | A workflow, secret, or connection string that would. |

The guard, in its own later build, asserts the ladder result and the subset check before it forwards a name. This file does not implement that guard.
